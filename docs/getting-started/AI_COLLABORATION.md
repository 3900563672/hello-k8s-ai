# 人类 × AI 协作手册

> 维护层：human | last-reviewed：2026-08-18 | 事实源：docs/MAP.yaml、源码、change-history/
> 面向项目所有者的「怎么指挥 AI」。AI 侧的工作流与约束见根目录 `AGENTS.md` + `docs/agents/WORKFLOW.md`（本地 Agent）与 `docs/remote-ai/README.md`（远程 AI）。

本仓库同时存在两类 AI 协作者，能力边界完全不同：

| 协作者 | 能力 | 交付方式 | 对应的提示词协议 |
| --- | --- | --- | --- |
| 本地 Agent（Codex / Claude Code） | 能操作本机仓库：改代码、跑测试、访问 GitHub、提交推送 | 直接落地到仓库，你审核 diff 与 CI | `AGENTS.md` + `docs/agents/WORKFLOW.md` |
| 远程 AI（网页版 ChatGPT / Claude） | 只能读你打包发过去的内容，在自己工作区分析、写方案或代码 | 把交付物带回，由本地 Agent 落地 | `docs/remote-ai/README.md` |

判断用谁：要"动手"（改文件、跑验证、提交）→ 本地 Agent；要"动脑"（方案、审查、长文分析）→ 两者都行，远程 AI 适合你想慢慢看产出、不想让它碰电脑的场景。

## 1. 一条好任务 = 五个要素

不管发给谁，任务信息越完整，返工越少：

1. **目标**：要达成什么结果（不是"做什么动作"）。
2. **边界**：改哪里、不改哪里；哪些是禁区和红线。
3. **约束**：风格、规模、提交方式、是否先出方案。
4. **验收**：怎样算完成（测试、CI、你确认过的东西）。
5. **交付**：汇报格式、提交/推送、文档同步要求。

缺哪个要素，Agent 会按 `docs/agents/WORKFLOW.md` 第 8 节的默认假设补，但你自己写清楚更可控。

## 2. 任务提示词模板（可复制）

### 模板 A：先探索、先给方案（不改代码）

```text
先别动手改代码。
1. 完整读一遍 <范围>（仓库 / 某模块 / 某文档）。
2. 分析现状：<问题或目标> 是什么原因、涉及哪些文件、有哪些选择。
3. 给出修改方针：改动清单、风险、工作量评估，模仿我仓库的现有风格。
4. 等我看过方案、确认改哪些之后，再开始执行。
```

典型用法：设计类任务、你还不确定要不要改的任务、涉及架构的改动。

### 模板 B：改代码（最小改动）

```text
帮我改 <问题描述>。
- 只做 <明确范围>，不做无关重构，不改业务行为（除非我要求）。
- 风格保持我仓库原样（提交信息用中文、单 commit、注释风格一致）。
- 改完自己验证：<能跑的检查都跑>，没问题再提交并推送。
- 汇报：改了什么 / 验证了什么（命令与结果）/ 没验证什么 / 真实风险。
```

典型用法：修 bug、小功能、重构抽取重复代码。

### 模板 C：先做一部分，做完再决定

```text
先做 <Phase 1 和 2>，做完自己检测，没问题就提交并推送。
暂时不考虑 <暂不关心的部分>，但 <必须保留的部分> 要保留。
```

典型用法：分批实施的大任务。你也可以在任务中间说"先别提交，等我看完"。

### 模板 D：GitHub / 看板操作

```text
1. 新建一个 issue，模仿我仓库既有 issue 的风格，模板：<design / bug / feat>。
2. 关联到 Project Review 看板，状态置 <To do / Approved>。
3. 完成 <N> 后关闭 issue，更新 change-history。
提交信息用我喜欢的仓库风格（中文、单 commit）。
```

### 模板 E：交给远程 AI（把打包内容发过去）

```text
附件是项目上下文包（生成时间见 CONTEXT_PACK.md 顶部）。
任务：<目标>。
请按 docs/remote-ai/README.md 的协议执行：
结论先行、标注依据文件、未验证的写"未验证"、按固定交接格式产出。
```

## 3. 好例子与坏例子（来自本仓库实际协作）

| 坏 | 好 |
| --- | --- |
| "帮我改一下" | "帮我修掉这两个 issue：<链接>。只修这两个，最小改动，改完验证并提交推送。" |
| "你看下这个代码" | "先别急着写代码，看一下 internal/controller 的包结构，有没有必要调整？给出理由，别改。" |
| "重构一下" | "全库抽取重复代码：控制器、前端、后端、模拟器都做。不改业务、风格不变、只抽重复代码段。" |
| "提交一下" | "提交并推送到 GitHub，提交信息用中文、单 commit，模仿我仓库风格。" |
| 不说环境 | "以后只走 WSL，直接帮我执行。" |

要点：**给 Agent 的每个任务都默认包含"最小改动 + 保风格 + 验证 + 汇报四段式"**，除非你明确说不用。

## 4. 如何审核 AI 的交付

每次交付后按顺序核对：

1. **git log**：提交信息是否符合仓库风格（`feat:` / `fix:` / `docs:` / `refactor:` + 中文 + `Fixes #N`）；一个任务是否只有一个 commit。
2. **change-history/**：是否有对应日期条目（四件套：README / IMPLEMENTATION_DETAILS / TEST_REPORT / MIGRATION_AND_ROLLBACK）。
3. **CI**：推送后 4 个 workflow（代码检查 / 文档检查 / 源码与部署验证 / E2E）是否全绿；docs-only 提交只看文档检查。
4. **汇报四段式**：改了什么 / 验证了什么（命令与结果）/ 没验证什么 / 真实风险。缺项就要求补齐。
5. **抽查 diff**：重点看是否越界（改了任务范围外的文件、改了生成文件、提交了不该提交的文件）。

## 5. 协作节奏建议

- **一个逻辑闭环 = 一个 commit**：中间过程让 Agent 用 `--amend` 或本地 squash；一天结束仍有多余 commit 就让 Agent 合并成当日汇总。
- **先小后大建立信任**：第一次让 Agent 只做 1-2 个文件的小任务；稳定后再放行整批（Project Review 看板默认每批上限 10 个）。
- **存档兜底**：大改动前先备份（例如把仓库打成压缩包放到你信任的位置），Agent 改坏了可以从中恢复。
- **文档跟着代码走**：代码改动必须同步 change-history；影响 README / 用户文档的，要求 Agent 一并更新并纳入同一提交（这是硬约束）。
- **保留你的否决权**：任何"自动闭环"（Agent 自己提 issue → 自己改 → 自己关闭）都以你审核过的 Project Review 条目为限，`To do / In review` 状态一律不许动代码。
