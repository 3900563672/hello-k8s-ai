# 事故 vs bug：为什么我们亲身踩过 WSL 服务层故障却没找到官方 bug

> 提升日期：2026-08-21 ｜ 来源：WSL 服务卡死事故复盘 + 社区同期源码级 issue 对照 ｜ 适用对象：本地 Agent
> 触发条件（Use when）：遇到系统级卡死/僵尸/异常，准备"修完环境就收工"时；或想从亲身事故产出官方 bug 报告时

## 现象

- 2026-08-21 我们亲身经历 wslservice 卡死：`wsl --shutdown` 后服务停在 StopPending、`wsl` 命令无限挂起、强杀 vmcompute 后电脑崩溃重启。
- 同一周，社区两个 issue（microsoft/WSL #41384/#41386）用反编译 wslservice.exe 的源码级分析定位到同一区域：init 事务无限超时持锁、CreateLxProcess 持锁等 OOBE 导致 shutdown 拿不到锁——创建当天就被维护者贴 bug。
- 对照：我们处理完事故后产出的是 SOP（怎么重启），他们产出的是 bug 报告（哪行代码错了）。我们手里有真实卡死场景，但没有追代码路径。

## 根因（四个偏差）

1. 问题定义：我们把现象定义为"事故"（目标=修好环境），社区定义为"bug"（目标=找到哪行代码错）。现象一消失我们就收工，从未在卡死现场问"这个锁链是什么代码写出来的"。
2. 研究侧选错：我们当时全部精力在 Linux 内核（seccomp/性能税/预构建内核），而我们的故障全部在 Windows 侧服务层（wslservice/wsl.exe 的状态机、锁、超时）。默认"服务卡死是系统状态问题不是代码问题"是错误的。
3. 门槛误判：我们预设"源码找明显 bug 轮不到我们，不然大家都拿 AI 找了"，主动放弃反向挖掘。事实是反编译 wslservice.exe 的提交者很少，门槛不在"AI 能不能找到"，而在"有没有人愿意用审计视角读 Windows 服务二进制"。
4. 精力形态：我们是顺手研究（主线是性能验证/环境修复），社区是专项审计（目标就是找逻辑错误）。阅读视角不同：理解视角（代码干什么）vs 审计视角（代码哪里会错）。

## 正确处置（下次遇到系统级故障）

1. 修环境前先存档证据：进程状态（StopPending/挂起）、wsl.exe 响应性、日志时间线、当时的操作序列。证据只花 1 分钟，事后无法补。
2. 修完环境后问一句："这个现象是哪行代码写出来的？" 若现象可确定性复现且属功能正确性（死锁/卡死/100% CPU/连接失败）而非性能权衡，就值得追到 Windows 侧服务层（反编译/符号 + 锁/超时/状态机视角）。
3. 产出格式按社区模板：源码归因（具体函数/锁/参数）+ 最小复现 + 排除环境噪音 + Expected/Actual + 修复建议。维护者 5 分钟能验证才算合格。
4. 性价比边界：不投入专职反编译；只在"恰好遇到 + 可复现 + 功能正确性"时按此流程走，成本约等于零。

## 边界

- 值得追：服务层死锁/卡死/竞态/连接失败（官方无辩解空间，认领快）。
- 不追：性能开销/行为差异（官方可归因权衡或环境，回应成本高，之前性能税线已验证）。
- 不要做的事：为了刷 issue 去专职反编译（与主项目目标冲突，边际收益低）。
