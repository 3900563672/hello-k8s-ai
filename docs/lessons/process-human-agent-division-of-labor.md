# 浏览器自动化与人工分工：API 优先、交互人工、失败即转交

> 提升日期：2026-08-20 ｜ 来源：journal/2026-08-20-notion-hub-browser-automation.md ｜ 适用对象：本地 Agent
> 触发条件（Use when）：涉及浏览器 UI 自动化（Notion / GitHub 网页 / 内部系统）；或需要决策"全自动 vs 人工操作"；或同一 UI 动作自动化连续失败 2 次

## 现象

- Notion 市集「添加模板」弹窗对自动化点击无反馈（实际已触发导入），真人一点即成功。
- Edge 经 FlClash 代理访问 Google / Notion 间歇 `ERR_PROXY_CONNECTION_FAILED`；PowerShell 走同一代理全通。
- Notion API（内部集成）不能创建 workspace 根级页面；浏览器「新增页面」自动化点击坐标偏移（点「集成」命中「通知我」），反复试错 20+ 分钟。
- 同一批操作转人工后 15 秒完成：建页面、共享集成、点模板添加。

## 根因

- 浏览器 UI 自动化依赖"DOM 快照 + 坐标点击"，菜单重渲染、悬浮层、坐标偏移都会静默失效；页面级交互（弹窗、权限授权、创建、市集添加）常要求真实用户手势。
- 自动化失败后的"再试一次"边际成本高：每轮 5-15 秒等待 + 快照 + 点击，代理不稳会放大重试次数。
- 人眼 + 人手对"当前屏幕"有零成本上下文，单次操作 10-30 秒；AI 每轮都要重建页面上下文（DOM 快照），且全部计入 token。

## 可复用规则

- **API/CLI 优先**：目标服务有 API（Notion API、gh、kubectl）就用 API；浏览器自动化只用于 API 覆盖不到的交互（拖拽、根级页面创建、权限授权、市集添加）。
- **交互密集 / 坐标敏感 / 多步菜单 → 人工**：单次人工 <30 秒的操作（建页面、点添加、共享集成），直接请用户点并给出精确步骤，不要自动化硬刚。
- **失败即转交**：同一 UI 动作自动化连续失败 2 次，停止重试，立即转人工并说明"点哪里、叫什么"。
- **点击前先取真实坐标**：菜单 / 浮层场景用 `playwright.evaluate(getBoundingClientRect)` 取坐标，再 `cua.click({x, y})`；不要盲信 `dom_cua` 的 node_id（存在坐标偏移）。
- **代理不稳不是代码问题**：浏览器页面间歇性代理失败时，先用 PowerShell 走同一代理验证目标可达；可达 = 代理正常，页面重试即可；频繁重试仍失败 → 转人工。
- **省 token 优先**：人工一步 10 秒 vs AI 自动化 20 分钟 + 数千 token，选人工；自动化是手段不是目的。

## 验证方法

- 新写浏览器自动化前先回答两问：① 有没有 API / CLI 能做？② 人工操作要几秒？任一答案命中则优先人工。
- 自动化连续失败 2 次后检查是否已转人工（硬规则，可在交付清单中自查）。
- 参考案例：Notion 模板添加 / 建根级页面 / 共享集成 = 人工；Notion 批量建库 / 改属性 / 删示例数据 = API。
