# 远程 AI 任务决策矩阵

> 维护层：remote ｜ last-reviewed：2026-08-18 ｜ 适用：每次任务开始时定位"我该做什么、交什么"

## 使用方式

1. 用一句话描述你的任务，对照下表找到最近似的一行。
2. 严格按该行的"输入/输出"执行；输出格式见 [DELIVERY.md](DELIVERY.md)。
3. 任务横跨多行时，以"交付物最重"的一行为主，其余作补充。

## 矩阵

| # | 任务类型 | 你需要什么输入 | 输出形态 | 注意点 |
| --- | --- | --- | --- | --- |
| 1 | 理解现状（"这个项目是什么 / 怎么做 X"） | 包 + 明确问题 | 结论先行摘要 + 依据路径 | 区分事实（源码/change-history）与推断；不写"文档说" |
| 2 | 审查代码/方案（"这个 PR/方案有没有问题"） | 包 + 具体 diff/方案 | 问题清单：严重度 + 位置 + 理由 + 建议 | 每个问题给出包内文件路径依据；不臆测未读代码 |
| 3 | 设计/方案（"怎么做 X，先给方针"） | 包 + 目标 + 边界 | 方案报告：现状 → 选择 → 推荐 → 风险 → 落地清单 | 优先复用仓库既有模式；说明与字段所有权/原则的兼容性 |
| 4 | 写代码（返回 diff，不落地） | 包 + 任务 + 约束 | 完整 diff + 逐文件说明 + 验证建议 | 最小改动；风格对齐仓库；不提交；标注未验证项 |
| 5 | 写文档（建议/草稿） | 包 + 目标读者 | 文档片段（Markdown）+ 放置路径建议 | 按读者分层（人类/Agent/远程 AI），不跨层混合 |
| 6 | 排障分析（"为什么报错 X"） | 包 + 日志/报错原文 | 根因分析 + "还需要哪些证据"清单 | 没有日志/集群时只能给证据清单，不假装定位 |
| 7 | 建 issue 草稿 | 包 + 问题描述 | 完整 issue 正文（标题/描述/验收标准） | 模仿仓库既有 issue 风格；标注优先级建议 |
| 8 | 评审另一 AI 的产出 | 包 + 对方交付物 | 逐项核对表：符合/偏离 + 证据 | 用本文件与 [PITFALLS.md](PITFALLS.md) 作检查清单 |

## 通用规则

- 输入不齐（缺目标/边界/验收）时，先列出你需要用户补充的问题，不要边猜边做。
- 输出一律用 [DELIVERY.md](DELIVERY.md) 的交接格式包裹。
- 无法访问的内容（GitHub、集群、真实日志）明确写"未验证/不可访问"，不编造。
